NUMERICS AND SOLVERS
STATUS: DRAFT v0.1 - for review

1. Libraries
------------------------------------------------------------------------
ndarray                                                          [ADOPT]
  ROLE  n-dimensional arrays: head/flow fields per pipe reach, sensor
        windows, scenario batches. The Rust counterpart of NumPy.
  WHY   Mature, widely used, integrates with rust-numpy for the Python
        bridge. MOC itself is mostly explicit loops over reaches, so we
        need clean arrays more than fancy linear algebra.
  EXIT  Plain Vec<f64> with our own indexing - easy.

faer (dense + sparse)                                            [TRIAL]
  ROLE  Linear algebra: sparse LU/Cholesky for the steady-state network
        solver (Newton / global gradient algorithm), SVD and least
        squares for Prony / matrix-pencil modal fits (04_), dense
        factorisations inside inference (05_).
  WHY   Pure Rust (no BLAS/LAPACK system dependency to ship), focus on
        correctness and performance, per-call parallelism control.
        nalgebra is aimed at small fixed-size geometry; not our need.
  RISKS Largely one principal maintainer [VERIFY current governance].
  EXIT  nalgebra-sparse / rsparse for sparse; LAPACK via FFI for dense.

rayon                                                            [ADOPT]
  ROLE  Data parallelism: many scenarios at once (localisation template
        libraries, synthetic training data, Monte Carlo over wave speed).
  NOTE  Parallelism must not break determinism (T3): reductions are done
        in a fixed order, never "whichever thread finishes first".

rustfft / realfft                                                [TRIAL]
  ROLE  Spectra, frequency-response functions, fast convolution for the
        unsteady-friction weighting function.

rand + rand_chacha + rand_distr                                  [ADOPT]
  ROLE  Random numbers for Monte Carlo and synthetic data.
  RULE  Always seeded ChaCha streams recorded with the run, so every
        stochastic result can be replayed exactly (P5).

statrs                                                           [TRIAL]
  ROLE  Distributions and special functions for likelihoods and tests.

CubeCL / wgpu (GPU compute)                                     [ASSESS]
  ROLE  Possible later: thousands of MOC scenarios in parallel on GPU for
        template libraries and ITA. One Rust kernel compiles to CUDA,
        ROCm, Metal, Vulkan/WGSL or CPU SIMD.
  WHY NOT NOW  CPU + rayon first; GPU only when profiling says so (T5).
        GPU floating point complicates determinism (T3).

2. Floating-point determinism                                   [BUILD]
------------------------------------------------------------------------
Bit-identical replay (P5, T3) is not automatic. Known causes of drift:
  - fused multiply-add (FMA) contracted on one CPU and not another;
  - libm differences in exp/log/sin/pow across platforms;
  - parallel reductions summing in a different order;
  - SIMD code paths chosen at runtime by CPU feature detection.
Policy:
  - Production results are defined on named targets (x86_64 Linux, and
    aarch64 Linux for gateways); CI replays golden events on each.
  - Explicit, fixed-order reductions; no parallel float reductions with
    non-deterministic ordering.
  - Transcendentals in hot physics paths go through one wrapper module,
    so we can swap in a portable implementation (e.g. the libm crate)
    if cross-platform drift is found.
  - Golden-file regression tests store results to the bit, and a
    tolerance test stores the physics-level accuracy separately.

3. Solvers we write ourselves                                    [BUILD]
------------------------------------------------------------------------
No library provides these at the quality, speed and auditability we need.
In build order:
  S1  Single-pipe MOC (reservoir-pipe-valve), quasi-steady friction,
      Courant = 1. Validates against Joukowsky, 2L/a and 4L/a (V-A1).
  S2  Boundary-condition library: reservoir, dead end, valve (orifice
      law with closure curves), junction (n-pipe, with minor losses),
      leak/burst (orifice and modified-orifice / FAVAD laws), pump
      (curve + inertia run-down), check valve, PRV, air valve, surge
      vessel.
      STATUS 2026-09-28: done - reservoir, dead end, valve + closure
      curves, junction (n-pipe + fixed outflow; minor losses not yet),
      leak/burst (two-way orifice incl. intrusion), ideal check valve.
      Validated in tests/hydraulics/analytical/boundaries (V-A3).
      Next - pump (curve + run-down), dynamic check-valve slam, PRV, air
      valve, surge vessel, FAVAD leak law.
  S3  Network MOC: global dt, integer reaches per pipe, wave-speed
      adjustment recorded as a known model error. Mass conservation to
      machine precision (V-A4).
  S4  Steady-state solver (initial conditions): global gradient algorithm
      (Todini-Pilati, as in EPANET) on faer sparse LU. We may cross-check
      against or temporarily use epanet-rs (03_).
  S5  Unsteady friction: Brunone/IAB first, convolution (Vardy-Brown,
      sum-of-exponentials) later.
  S6  Viscoelastic walls: 1-3 Kelvin-Voigt elements for PE/PVC.
  S7  Cavitation: DGCM (discrete gas cavity model), DVCM for comparison.
  S8  Discrete adjoint of the network MOC - exact gradients of a data
      misfit w.r.t. wave speeds, friction, leak parameters, in one
      backward pass. Enables gradient-based ITA and HMC (05_). This is
      one of our differentiators (11_).
  S9  Frequency-domain transfer-matrix model for small-amplitude
      analysis and frequency-response methods.
Each solver ships with: analytical tests, a TSNet cross-check where TSNet
supports the case, property tests (conservation, symmetry, reversibility
of frictionless cases), and a benchmark.

Sources checked 2026-09-28: faer docs (sparse LU/Cholesky); CubeCL repo;
Gaffer On Games and FLiT on floating-point determinism.
