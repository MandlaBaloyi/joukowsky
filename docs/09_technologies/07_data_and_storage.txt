DATA AND STORAGE
STATUS: DRAFT v0.1 - for review

Three kinds of data with different shapes (03_sensing_and_signal):
  (a) raw high-rate event windows - immutable evidence; replayed forever;
  (b) continuous low-rate series - 1 Hz summaries, Tier 0/1 loggers;
  (c) metadata - networks, sensors, clocks, events, labels, model
      versions. Relational, versioned.
One database for all three would be wrong for at least two of them.

1. Raw event windows -> columnar files on object storage
------------------------------------------------------------------------
Apache Arrow (arrow-rs) in memory, Parquet on disk              [TRIAL]
  WHY   Columnar, compressed, typed, readable from Rust, Python, SQL
        engines. Immutable files suit evidence that must never change.
object_store crate (S3-compatible: AWS S3 af-south-1, Azure Blob,
GCS, MinIO on-prem)                                             [TRIAL]
  WHY   One API across clouds; no lock-in to one provider.
Zarr v3 via zarrs                                               [ASSESS]
  Alternative for large multi-dimensional simulation outputs (scenario
  libraries: scenario x sensor x time). Mature Rust implementation,
  conformant with Zarr 3.1. Decide when template libraries get large.
RULE  Raw samples, raw timestamps and clock-quality metadata are stored
      as received, never overwritten (time_synchronisation.txt item 4).
      Corrections are new derived files that reference the original.

2. Low-rate time series
------------------------------------------------------------------------
PostgreSQL with native time partitioning                        [ADOPT]
  DECISION TD-008. Dev on the owner's local PostgreSQL 18; production
        on AWS (af-south-1). One database for time series AND metadata.
TimescaleDB (PostgreSQL extension)                              [ASSESS]
  WHY   Continuous aggregates, compression. Only if measured load
        needs it.
  CHECK Licence: parts of TimescaleDB are under the Timescale License,
        not Apache-2.0 - acceptable for self-hosting but restricts
        offering it as a DB service [VERIFY terms at adoption].
QuestDB                                                         [ASSESS]
  Much faster ingest and analytics in benchmarks (vendor-published -
  treat with care). Switch only if measured load at national scale
  (~10k sensors) requires it (T5).
InfluxDB 3                                                      [ASSESS]

3. Metadata, network geometry, labels
------------------------------------------------------------------------
PostgreSQL + PostGIS                                            [TRIAL]
  Network geometry (pipes as linestrings, coordinates of sensors),
  spatial queries for the operator map. Versioned network models: every
  change is a new version, never an in-place edit (P5).
sqlx (async, compile-time-checked SQL from Rust)                [TRIAL]
geo / geo-types / proj crates                                   [ASSESS]
  Coordinate handling and SA projections (Lo / Hartebeesthoek94)
  [VERIFY which CRS partners use].

4. Analytics and research queries
------------------------------------------------------------------------
Apache DataFusion (embedded SQL engine over Arrow/Parquet)      [ASSESS]
Polars (DataFrames, Rust and Python)                            [ASSESS]
DuckDB (analyst workstation)                                    [ASSESS]
  For offline studies over years of events; not in the hot path.

5. Retention (to decide with partners and POPIA advice)
------------------------------------------------------------------------
  - Raw event windows: kept indefinitely (they are the training data and
    the audit trail).
  - Continuous raw high-rate streams (if a source sends them): rolling
    window, e.g. 30-90 days, then summaries only [DECIDE].
  - Load estimate from 06_: 10,000 Tier 2 sensors x ~22 MB/day
    ~ 220 GB/day raw before compression.
